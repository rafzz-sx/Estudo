  🚨 0-A. PRIMEIRA COISA, HOJE — O SEGREDO DO LOGIN PODE SER PÚBLICO
================================================================================

  Este é o item mais urgente do arquivo. Leva 1 minuto para verificar.

  O QUE ACONTECE
  --------------
  Em  batcaverna/apps/web/src/lib/auth.ts  (linha 3):

      const JWT_SECRET = new TextEncoder().encode(
        process.env.JWT_SECRET || 'dev-secret-change-me'
      );

  Se a variável JWT_SECRET NÃO estiver configurada na Vercel, o segredo que
  assina o login de todos os alunos é a string  'dev-secret-change-me'  —
  escrita neste repositório, que é público.

  POR QUE ISSO É PIOR QUE A CHAVE DO BANCO
  ----------------------------------------
  Com esse segredo, qualquer pessoa que leia o repositório monta sozinha um
  token dizendo "eu sou administrador", cola no navegador e entra no painel
  admin. Não precisa de senha, não precisa da chave do banco, não precisa
  saber o e-mail de ninguém.

  De lá se lê tudo: dados dos alunos, conversas privadas do chat, chamados
  de suporte.

  O QUE FAZER AGORA (1 minuto)
  ----------------------------
     1. Abra https://vercel.com/dashboard
     2. Projeto da BatCaverna → "Settings" → "Environment Variables"
     3. Procure  JWT_SECRET

     SE ELA EXISTIR e estiver marcada em Production:
        Confira que o valor NÃO é 'dev-secret-change-me'. Se for outro
        valor longo e aleatório, você está protegido. Siga para o 0-B.

     SE ELA NÃO EXISTIR:
        A plataforma está aberta agora. Crie imediatamente:
          - Nome:  JWT_SECRET
          - Valor: uma sequência longa e aleatória (mínimo 40 caracteres).
                   Pode gerar em https://www.random.org/strings/ ou apenas
                   digitar bastante coisa sem sentido.
          - Marque Production / Preview / Development
        Depois: "Deployments" → "Redeploy" no último deploy.

        Efeito colateral esperado: todo mundo é deslogado e precisa entrar
        de novo. Isso é o certo — invalida qualquer token forjado.

  DEPOIS, ME PEÇA
  ---------------
  Eu removo o  || 'dev-secret-change-me'  do código e faço a aplicação
  recusar-se a subir sem a variável. Assim o problema não pode voltar
  calado. (Não faço agora porque, se a variável não estiver configurada,
  isso tiraria o site do ar.)


================================================================================
  🚨 0-B. A DESCOBERTA QUE MUDA A ORDEM DAS COISAS
================================================================================

  O QUE EU ENCONTREI NA AUDITORIA
  -------------------------------
  Em  batcaverna/apps/web/src/lib/supabase.ts  (linha 27):

      const key = envServiceKey.includes('service_role')
                  ? envServiceKey
                  : SUPABASE_SERVICE_KEY;

  A intenção era: "se a variável de ambiente tiver uma chave de serviço
  válida, use ela; senão, use a do arquivo".

  O problema: uma chave do Supabase é um JWT, e num JWT o texto
  "service_role" fica guardado em base64 — NÃO aparece como palavra legível.

  Eu testei com a própria chave do seu projeto:

      a chave contém o texto 'service_role'?   ->  NÃO
      a função (role) decodificada da chave:   ->  service_role

  Ou seja: a condição é SEMPRE falsa.

  ✅ CORRIGIDO NO CÓDIGO EM 07/09 (commit "impl"). VALE A PARTIR DO
     PRÓXIMO DEPLOY.

  A comparação quebrada foi trocada por uma que reconhece o FORMATO da
  chave (JWT `eyJ...` ou `sb_...`). Com isso:

      • a variável de ambiente, quando existe, MANDA;
      • o valor fixo do arquivo virou reserva, usada só se a variável
        faltar;
      • o mesmo vale para a chave pública e para a URL do projeto — agora
        dá para apontar para outro projeto Supabase só pela Vercel.

  O QUE ISSO MUDA NA ORDEM: depois que você cadastrar as variáveis (Passo
  2 do 0-C) e este código estiver no ar (Passo 3), rotacionar é seguro —
  NÃO precisa mais esperar eu tirar o valor fixo do arquivo. Tirá-lo virou
  higiene (Passo 7, opcional), não pré-requisito.

  Enquanto este código NÃO estiver no ar, a situação continua a de antes:
  a variável é ignorada e rotacionar derruba o site. Por isso o Passo 3.

  (Histórico, para entender o que aconteceu: a comparação era
  `includes('service_role')`, e num JWT esse texto fica em base64 — nunca
  aparece legível. A condição era sempre falsa.)

  4. SUPABASE — BACKUP E RECUPERAÇÃO
================================================================================

  A DIFERENÇA ENTRE OS DOIS (importa muito)

  Backup automático diário
    Uma fotografia do banco, uma vez por dia. Se der problema, você volta
    para a foto mais recente.
    Se o backup foi às 3h e o problema foi às 22h, você perde 19 horas de
    estudo, XP e conversa dos alunos.

  Point-in-Time Recovery (PITR)
    Grava tudo continuamente. Você volta para QUALQUER minuto dos últimos
    7 dias — inclusive "um minuto antes do DELETE errado".
    É pago (add-on do plano Pro).

  O QUE VERIFICAR
  1. https://supabase.com/dashboard → seu projeto
  2. Menu lateral → "Database" → "Backups"
  3. Veja o que aparece:

     Plano Free      → SEM backup automático. Você está por sua conta.
     Plano Pro       → backup diário, guardado por 7 dias
     Pro + add-on    → PITR disponível para ativar

  SE VOCÊ ESTIVER NO PLANO FREE
  Faça um backup manual com regularidade:
     1. Dashboard → Database → Backups → "Download backup"
     ou, com a CLI instalada:
     supabase db dump -f backup-$(date +%F).sql

  RECOMENDAÇÃO
  A plataforma guarda progresso de estudo de menores de idade. Sem backup
  você não tem como reparar um acidente. É o item de maior custo-benefício
  depois dos itens 0.

  E FAÇA UM BACKUP ANTES da rotação de chaves (Passo 5 do item 0-C).

================================================================================
  7. PONTOS QUE EXIGEM DECISÃO SUA (não são ação de painel)
================================================================================

  Estes três a auditoria encontrou, eu consigo corrigir por código, mas
  envolvem uma escolha que é sua:

  7.1  SENHA GUARDADA COM SHA-256 SIMPLES
       Hoje a senha vira um hash SHA-256 direto, sem "sal" e sem função
       lenta. Se a tabela `users` vazar, senhas comuns são descobertas
       rapidamente com placa de vídeo.
       O certo é PBKDF2 (funciona no ambiente da Vercel).
       DECISÃO SUA: a migração precisa reprocessar a senha de cada pessoa
       no próximo login dela. Quem não entrar mais nunca fica com o hash
       antigo. Não há como converter sem a senha em mãos.

  7.2  TOKEN DE LOGIN GUARDADO NO NAVEGADOR
       Os cookies são httpOnly (JavaScript não lê) — mas os MESMOS tokens
       também ficam no localStorage, onde qualquer script lê. A proteção do
       cookie fica anulada.
       Como as APIs já aceitam o cookie, dá para parar de guardar os tokens
       no localStorage sem perder nada.
       DECISÃO SUA: só quero seu aval porque mexe no fluxo de login, e
       prefiro fazer num momento em que você possa testar.

  7.3  REPOSITÓRIO PRIVADO x HISTÓRICO DO GIT
       Tornar privado (Passo 1) esconde o repositório, mas quem já clonou
       continua com a cópia, inclusive o histórico com as chaves antigas.
       Por isso a rotação (Passo 5) é obrigatória, não opcional.
